Лабораторна робота №5

Мікросервіси з використанням Service Discovery та Config Server
на базі HashiCorp Consul

1. Мета роботи

Замінити власний Config Server з Лабораторної роботи №4 на HashiCorp Consul, який виконує одразу чотири ролі:

  • Service Registry — автоматична реєстрація мікросервісів при старті.
  • Service Discovery — facade-service отримує актуальні адреси сервісів з Consul.
  • Config Server (KV Store) — конфігурація Hazelcast та Message Queue зберігається в Consul KV без хардкодування в коді.
  • Health Monitoring — Consul автоматично відстежує стан сервісів і виключає недоступні екземпляри.

2. Архітектура системи

┌─────────────────────────────────────────────────────────────┐ │ Consul :8500 │ │ Service Registry │ KV Store │ │ logging-service (×3) │ config/hazelcast/cluster-members │ │ counter-service │ config/queue/name │ │ facade-service │ │ └─────────────────────────────────────────────────────────────┘ ▲ register / health-check / discover │ Client ──► facade-service :50050 │ ├──gRPC──► logging-service-1 :50051 ──► Hazelcast IMap ├──gRPC──► logging-service-2 :50051 ──► Hazelcast IMap └──gRPC──► logging-service-3 :50051 ──► Hazelcast IMap │ └──Queue──► Hazelcast IQueue │ counter-service :50060 │ PostgreSQL :5435

Усі мікросервіси при старті реєструються в Consul і надають health check. facade-service перед кожним запитом запитує Consul про список healthy екземплярів logging-service і рівномірно розподіляє навантаження між ними.

3. Consul KV — конфігурація

3.1 Bootstrap-скрипт (consul-bootstrap/bootstrap.sh)

Окремий контейнер consul-bootstrap чекає на готовність Consul і записує початкові значення в KV Store: 

#!/bin/sh
CONSUL_URL="http://consul:8500"

# Чекаємо, поки Consul обере лідера
until curl -sf "${CONSUL_URL}/v1/status/leader" > /dev/null; do
  sleep 1
done

# Адреси вузлів Hazelcast-кластера
curl -X PUT "${CONSUL_URL}/v1/kv/config/hazelcast/cluster-members" \
  -d "hazelcast-1:5701,hazelcast-2:5701,hazelcast-3:5701"

# Назва черги повідомлень
curl -X PUT "${CONSUL_URL}/v1/kv/config/queue/name" \
  -d "counter-queue"

4. Реалізація

4.1 Реєстрація сервісу в Consul (logging-service)

Кожен екземпляр реєструється з унікальним service_id та TCP health check: 

import consul

def register_with_consul():
    c = consul.Consul(host=CONSUL_HOST, port=CONSUL_PORT)
    c.agent.service.register(
        name="logging-service",
        service_id=SERVICE_ID,          # наприклад, "logging-1"
        address=MY_HOST,                # hostname контейнера
        port=LOG_PORT,                  # 50051
        check=consul.Check.tcp(
            MY_HOST, LOG_PORT,
            interval="10s",
            timeout="5s",
            deregister="30s"            # авто-видалення після 30 с недоступності
        ),
    )

4.2 Читання конфігурації з Consul KV

Сервіси зчитують конфігурацію при старті замість файлів або змінних середовища: 

def get_kv(c, key: str) -> str:
    _, data = c.kv.get(key)
    return data["Value"].decode()

# logging-service: отримуємо адреси Hazelcast-кластера
cluster_str = get_kv(c, "config/hazelcast/cluster-members")
addresses   = cluster_str.split(",")
hz = hazelcast.HazelcastClient(
    cluster_members=addresses,
    cluster_name="dev"
)

# counter-service: отримуємо назву черги
queue_name = get_kv(c, "config/queue/name")
queue = hz.get_queue(queue_name).result()

4.3 Service Discovery у facade-service

Перед кожним gRPC-викликом facade-service запитує Consul про список здорових екземплярів: 

def get_healthy_logging_addresses() -> list[str]:
    c = consul.Consul(host=CONSUL_HOST, port=CONSUL_PORT)
    _, services = c.health.service("logging-service", passing=True)
    return [
        f"{s['Service']['Address']}:{s['Service']['Port']}"
        for s in services
    ]

7. Перевірка відмовостійкості

7.1 Вимкнення logging-service-1

$ docker stop lab5-logging-service-1-1

Через ~15 секунд (інтервал health check) Consul позначає екземпляр як critical і виключає його зі списку healthy: 

$ curl 'http://localhost:8500/v1/health/service/logging-service?passing=true'
logging-2  logging-service-2:50051
logging-3  logging-service-3:50051

Нові запити продовжують оброблятися без помилок:

$ curl -X POST http://localhost:50050/ -d '{"msg": "msg11"}'
{"uuid":"2e93a31b-...","msg":"msg11"}   ← успішно через logging-2 або logging-3

7.2 Відновлення logging-service-1

$ docker start lab5-logging-service-1-1

Після проходження health check Consul повертає екземпляр у список:

$ curl 'http://localhost:8500/v1/health/service/logging-service?passing=true'
logging-1  logging-service-1:50051
logging-2  logging-service-2:50051
logging-3  logging-service-3:50051

7.3 Призупинення counter-service (docker pause)

$ docker pause lab5-counter-service-1

$ curl -X POST http://localhost:50050/ -d '{"msg": "msg12"}'
{"uuid":"e69e021b-...","msg":"msg12"}   ← POST успішний, повідомлення в черзі

$ curl http://localhost:50050/
msg1 ... msg11 null   ← counter повертає null (сервіс недоступний)

Після відновлення counter-service вичитує накопичені повідомлення:

$ docker unpause lab5-counter-service-1

[counter-service] Consumed from queue: 'msg12'
[counter-service] Consumed from queue: 'msg13'
[counter-service] Consumed from queue: 'msg14'

$ curl http://localhost:50050/
msg1 msg2 msg3 msg4 msg5 msg6 msg7 msg8 msg9 msg10 msg11 msg12 msg13 msg14
Черга Hazelcast зберігає повідомлення навіть при недоступності counter-service. Після відновлення сервіс автоматично вичитує всі накопичені записи — дані не втрачаються.

8. Consul UI

Веб-інтерфейс Consul доступний за адресою http://localhost:8500/ui і надає зручний огляд стану системи:

  • Services — список усіх зареєстрованих сервісів з індикатором стану: зелений (healthy) / червоний (critical).
  • Key/Value — перегляд і редагування значень у KV Store (config/hazelcast/cluster-members, config/queue/name).
  • При зупинці будь-якого контейнера його статус автоматично змінюється на critical після закінчення інтервалу health check — без будь-якого ручного втручання.

9. Висновки

У ході лабораторної роботи власний Config Server з попередньої роботи було повністю замінено на HashiCorp Consul, який одночасно виконує роль Service Registry, Service Discovery, Config Server та Health Monitor. Сервіси динамічно реєструються при старті та автоматично видаляються зі списку доступних при виявленні недоступності — без жодного ручного втручання.

Конфігурація Hazelcast-кластера та назва черги повідомлень зберігаються в Consul KV Store, що усуває хардкодування параметрів у коді та спрощує зміну конфігурації без перезбірки образів. facade-service завжди отримує актуальний список здорових екземплярів через Consul Health API, що забезпечує коректний балансування навантаження.

Тестування відмовостійкості підтвердило: при вимкненні одного з logging-service трафік автоматично перенаправляється на доступні екземпляри; при призупиненні counter-service повідомлення накопичуються в черзі Hazelcast і обробляються після відновлення сервісу без втрати даних. Система демонструє повну відмовостійкість на рівні кожного компонента.
